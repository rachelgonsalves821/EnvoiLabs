# Rate-limit store and route integration handoff

This is a synthetic contract and implementation plan. Gate 2 is the assigned writer for shared Platform migrations. Gate 1 released the six named sign-in/upload paths for Gate 4 wiring on November 24. The three POST paths now call the Gate 4 decision seam before OTP dispatch or audio reservation. The call is disabled by default and in production; no real store is connected until Gate 2's migration lands.

## Preview-only source and configuration boundary

The explicit opt-in is `GATE4_RATE_LIMIT_PREVIEW_ENABLED=1` on a Vercel preview deployment only. Enabling it without a connected atomic store, valid source, dedicated HMAC key, or all policy values yields a generic 503 before the protected action. The source adapter reads only Vercel's `x-vercel-forwarded-for`, requiring exactly one valid IP. It rejects lists, malformed addresses, and zone identifiers; `x-forwarded-for` and `x-real-ip` are ignored. [Vercel's request-header documentation](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for) describes its platform header and proxy distinction. Header ownership must still be verified in the actual preview ingress with a spoofed client request before enabling this path.

`GATE4_RATE_LIMIT_HMAC_KEY` is dedicated to these quota digests and must contain at least 32 bytes. The required, positive-integer knobs are `GATE4_RATE_LIMIT_WINDOW_SECONDS`, `GATE4_RATE_LIMIT_EMAIL_PER_ADDRESS`, `GATE4_RATE_LIMIT_EMAIL_PER_SOURCE`, `GATE4_RATE_LIMIT_AUDIO_PER_RESPONDENT`, and `GATE4_RATE_LIMIT_AUDIO_PER_SOURCE`. No values or secret are committed to deployment configuration. Synthetic tests supply a disposable key and values in memory. This code does not set a production secret or enable any quota.

## Exact Gate 2 migration request

Add one ordered Platform migration that creates `internal.gate4_rate_windows` and `public.consume_gate4_rate_limit(requested_rules jsonb) returns jsonb`. The RPC request is exactly two objects with `surface`, `key_kind`, `key_digest`, `max_attempts`, and `window_seconds`. The response is either `{"allowed":true}` or `{"allowed":false,"retry_after_seconds":N}` with an integer `N >= 1`. The current [Gate 4 RPC adapter](../../apps/web/server/gate4/rate-limit-store.ts) maps that wire shape to its atomic store port; an RPC error, null, or malformed result fails closed as unavailable.

The private table needs `surface text`, `key_kind text`, `key_digest text`, `window_start timestamptz`, `attempts integer`, and `expires_at timestamptz`, with a primary key on `(surface, key_kind, key_digest, window_start)`. Constrain surface/kind combinations to `email-start` with `email` or `source`, and `audio-upload` with `respondent` or `source`; constrain digest to 64 lowercase hex characters and attempts to a nonnegative integer. Enable RLS, deny direct `anon`, `authenticated`, and `service_role` access, and grant only the restricted RPC to `service_role`. The RPC should be `SECURITY DEFINER` with an empty pinned search path and fully qualified references. Include both objects in the all-table RLS/privilege matrix and generated public database types.

The function must validate an array of exactly two distinct rules for one surface, with one identity key and one source key. It must reject invalid digests, nonpositive or excessive limits/windows, duplicate keys, and policy mismatches without writing counters. The proposed values stay configurable: store approved `(surface, key_kind, max_attempts, window_seconds, enabled)` in a private policy table or enforce an equivalent versioned server-side configuration; reject a caller's rule when it differs from the active approved policy. Start disabled. Gate 2 and the coordinator should choose the policy owner and rollout mechanism before a migration is merged.

For an allowed request, acquire transaction-scoped advisory locks for both `(surface, key_kind, key_digest)` identities in deterministic order, then read database time once. Calculate each fixed window from that time, check both counters, and increment both in the same transaction. If either is exhausted, increment neither and return the **maximum** remaining seconds among exhausted windows as the generic retry interval. A hash collision in the advisory-lock key may add contention but must never allow an over-limit decision. A database error must propagate to the adapter, which returns 503 before downstream action. Prune expired rows after at most 24 hours through a separately owned maintenance job or bounded batch; do not log the digests. A verified atomic `INSERT ... ON CONFLICT`/row-lock implementation is also acceptable if it gives the same all-or-none result under two sessions.

Gate 2's disposable database checks should run two concurrent sessions consuming the same pair, assert exactly the configured number of grants, and verify no partial increment when one key is exhausted. Also check window rollover, different emails behind one source, one email across sources, distinct respondent keys, malformed requests, service-only function execution, denied direct table reads, and disabled/mismatched policy. Do not ship a migration with a production-enabled default.

## Exact Gate 1 handler-path request

After Gate 1 releases the paths, Gate 4 can wire only the limiter call and adjacent tests in:

| Handler/service | Insertion point | Required response behavior |
| --- | --- | --- |
| `apps/web/app/api/respondent/auth/start/route.ts` → `apps/web/server/auth/respondent.ts:respondentStart` | After existing origin/JSON, normalized email, age, and service configuration checks; before `signInWithOtp`. | `allow` continues unchanged. `limited` returns generic 429 and bounded `Retry-After`, without OTP call or age-proof cookie. `unavailable` returns generic 503 without OTP call. Preserve current generic success and callback behavior. |
| `apps/web/app/api/researcher/auth/start/route.ts` → `apps/web/server/auth/researcher.ts:researcherStart` | After existing input/email/service checks; before `signInWithOtp`. | Same 429/503 mapping, no OTP call, and preserve `shouldCreateUser:false`, generic success and pending PKCE verifier semantics for accepted requests. |
| `apps/web/app/api/respondent/answers/upload/route.ts` → `apps/web/server/respondent/private-audio.ts:startAudioUpload` | After request/size/MIME validation and authenticated `getClaims()`; before `reserve_gate1_audio` and `createSignedUploadUrl`. | Use the authenticated subject UUID as the per-respondent account key; `respondents.auth_user_id` is unique. A 429/503 must create no reservation, object path, or signed URL. Invalid/unauthenticated calls do not reveal quota state. |

Both sign-in routes must call the same `emailStart` policy and database surface so switching between respondent and researcher cannot bypass an email or source cap. The upload surface is separate. The request source must come from the reviewed preview ingress adapter, not a user-controlled forwarded header; if unavailable under the preview opt-in, fail closed. Gate 4 owns the dedicated HMAC key interface and disposable local/preview test configuration, but no production secret is created or set. Store only versioned HMAC digests; rotate the secret after old windows expire. Keep error/denial logs aggregate and key-free.

The [route-level acceptance matrix](security-review.md#distributed-limit-test-handoff) applies after the real store is connected. Current synthetic route tests establish that limiter denial prevents OTP dispatch and audio reservation/signing, and that invalid or unauthenticated uploads do not reveal quota state. Run the integrated matrix against two web processes sharing the migrated database, with a disposable Auth/storage stack and spyable OTP/reservation/signing ports. Signed object transfer still needs storage-side size, MIME, path, expiry and bandwidth checks. This remains a separate Gate 4 acceptance slice; the preview path is not enabled.
