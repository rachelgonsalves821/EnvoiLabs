One concrete Gate 2 service correction should precede the payout fixture: #130 currently catches *every* `reserveSessionPayout` error and returns `blocked`, including a database outage. Its existing test covers a cap rejection but not an unavailable store. The adapter needs a typed policy rejection versus transient failure so a transient outage remains retryable and is not shown as a permanent payout denial. The fault fixture should inject both outcomes and verify that neither calls the provider, while only the transient path is retried with the same logical payout.

Security checks at each handoff: use only fictional respondent and provider identifiers, assert service-only RPC privileges and all-table RLS on the integrated migrations, preserve the same logical idempotency key across retries, and inspect failure logs for raw answers, contact details, signed URLs, or provider payloads. The final Tremendous and Stripe adapters must authenticate provider events and re-read provider state; the draft services accept typed observations but do not establish live webhook authenticity. Gate 4 needs the exact adapter, job-control, report/export, and probe-control identifiers from Gates 2 and 3 before these fixtures can run end to end.
