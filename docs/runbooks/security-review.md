## Rate-limit path inventory and acceptance cases

The route file is a thin handler; the service path named here calls the Gate 4 decision before the expensive or externally visible action as of draft PR #113 head `7ac8cf5`. The opt-in is preview-only and now resolves the service-only RPC adapter when enabled; no current deployment has that setting or has proven end-to-end application-level distributed protection. Supabase returning 429 is a secondary provider guard.

| Surface | Route → current service/action | Required local acceptance cases after Gate 1 handoff |
| --- | --- | --- |
| Respondent email link | `POST /api/respondent/auth/start` → `server/auth/respondent.ts:respondentStart` → `signInWithOtp` | Same normalized email and source exceed policy: 429 before OTP call. Separate emails from one source and one email across sources are bounded. Concurrent requests cannot all pass. Valid traffic recovers when the window ends. Generic responses do not reveal account existence. |
| Researcher email link | `POST /api/researcher/auth/start` → `server/auth/researcher.ts:researcherStart` → `signInWithOtp` | Same cases; preserve `shouldCreateUser:false`, generic response, and pending PKCE verifier. |
| Signed audio upload reservation | `POST /api/respondent/answers/upload` → `server/respondent/private-audio.ts:startAudioUpload` → `reserve_gate1_audio` and `createSignedUploadUrl` | Authenticated respondent is bounded before reservation and signing. 429 creates no reservation or URL. Concurrent requests converge under one quota. Another respondent cannot consume the same per-account quota. Invalid or unauthenticated calls do not reveal quota state. |
| Direct object transfer | Browser uploads to a Supabase signed URL after reservation. | Verify storage-side size, MIME, object path, URL expiry, and service or edge limits; API request limits alone do not bound transfer bandwidth. |

Also inspect `POST /api/respondent/answers/record` for typed-answer abuse and confirmation costs. It is not a substitute for the required sign-in and upload controls. The acceptance test implementation belongs with the eventual limiter after Gate 1 releases these paths.

### Distributed-limit test handoff

Gate 1 released the six named auth/upload files for this rate-limit insertion on November 24, recorded in the shared `gate-1.md` handoff. Gate 4 changed only those start/upload paths and adjacent tests. The limiter's shared atomic store remains Gate 2's migration responsibility; in-memory per-instance counts cannot establish a distributed limit.

Prepare a disposable integration fixture with two independent app processes pointing to one limiter store and one local Auth/storage stack. Freeze or advance the clock at the limiter boundary, and instrument OTP dispatch, `reserve_gate1_audio`, and signed URL creation. Assertions to add alongside the eventual implementation:

1. Send `N + 1` concurrent respondent OTP starts with the same normalized email and source across both processes, where `N` is the configured policy threshold. Exactly `N` may reach OTP dispatch; excess requests must return 429 and no dispatch. Repeat for researcher starts, preserving `shouldCreateUser:false` and a usable PKCE callback for accepted requests.
2. Vary email while holding source constant, then vary source while holding email constant. Both dimensions must be bounded under the approved policy. Compare unknown and known accounts for the same public response shape. Verify the same normalized email spelling shares a quota without storing plaintext email in the limiter key.
3. Advance beyond the window and confirm a valid request succeeds; confirm a malformed or cross-origin request is rejected before quota consumption and no account existence or quota balance leaks.
4. With a synthetic authenticated respondent and eligible answer, send `N + 1` parallel upload-reservation calls through both processes. At most `N` reach the reservation RPC and signed URL creation. Every 429 leaves no new reservation, object path, or signed URL. A second respondent retains a separate allowance; unauthenticated and invalid-answer requests reveal no quota state.
5. Exercise direct signed object transfer separately for size, MIME, path binding, expiry, and bandwidth policy. The application limit on URL creation does not enforce storage transfer volume.

Run these cases against the real distributed store in local integration and preview after Gate 1 handoff. The threshold symbol `N` avoids inventing a production policy in this preparatory review.

The coordinator approved the [Postgres atomic store and HMAC direction](rate-limit-proposal.md) for synthetic preparation. The exact migration and candidate thresholds have not been enabled.

### Isolated limiter security checkpoint

The Gate 4-owned decision module rejects missing or malformed policy, a short HMAC secret, absent/untrimmed source, invalid identity, and store failure before returning `allow`. The synthetic RPC adapter sends only hashed keys and maps null/error/malformed replies to an unavailable result. The standalone response helper uses the existing private, no-store and no-referrer headers with generic 400/429/503 bodies and a bounded `Retry-After`. Focused tests exercise these behaviors and two limiter instances sharing one atomic fixture. This is a code-path review, not proof that a real route is limited.

The [exact migration and route handoff](rate-limit-integration.md) remains a security dependency. Gate 2 must demonstrate all-or-none Postgres increments, disabled-by-default policy, service-only function execution, denied direct table access, cleanup, and generated types. Gate 4 owns the dedicated HMAC key interface and preview source parser; actual Vercel header ownership still needs a spoofed-client preview check. Synthetic handler tests now prove no OTP, reservation or signed URL on 429/503. Two-process tests against the real store, recovery, and direct signed-object transfer controls remain open. No production limiter is enabled by this checkpoint.

## Draft marketplace feasibility privacy review

Read-only review of Gate 2 [draft #151](https://github.com/rachelgonsalves821/EnvoiLabs/pull/151) at `fcadff8` found the route disabled by default, requiring an AAL2 researcher claim before a service-role RPC; the RPC checks the target study's organization and state. The response uses private, no-store headers. The internal candidate function denies direct app-role execution. These are useful boundaries, but they do not close the following disclosure risk.

`read_gate2_marketplace_feasibility` returns exact `eligibleProfileCount` and exact prior `offered`/`accepted`/`completed` counts for the target's criterion-selected candidate cohort. Its draft pgTAP fixture intentionally returns `eligibleProfileCount=1` and `completed=1`. The history joins invitations and sessions from **other studies without an organization filter**. A researcher who can obtain multiple narrowly scoped, pre-payment studies could compare small cohorts or changing eligibility and infer another person's profile match or past participation. There is no application-level request budget on this GET route. This is a source-review privacy finding, not a demonstrated exploit or a claim that a respondent ID is directly returned.

Before enabling this endpoint, Gate 2 should choose and test a small-cohort disclosure policy (for example suppress or band exact counts below an approved threshold), constrain repeat/differencing queries with an authorized study/scope snapshot and request budget, and decide whether cross-organization history may be exposed at all. A regression should make two fictional studies differ by one sensitive criterion with a single eligible profile and verify that the public response cannot reveal an exact 0-versus-1 or prior-completion difference; keep the private candidate ID and service RPC inaccessible to browser roles. Gate 4 will re-review the integrated route and RLS matrix after the owning branch lands. No Gate 2 file was edited in this review.

## Draft referral fraud boundary

Read-only review of Gate 2 draft #156 `dd1ffa4` found private referral verification and vesting tables, revoked browser-role reads and service-role writes, authenticated attribution/verification RPCs, a unique referee, and a normalized-email digest uniqueness constraint. `register_gate2_referral` rejects self-referral and a conflicting referrer for one referee. It does not inspect whether the selected referrer is already attributed to this referee or is part of a longer referral cycle. In a disposable combined Gate 4/Gate 2 database, two fictional active, confirmed users successfully called `register_gate2_referral` with each other's codes in one rolled-back transaction: both reciprocal results were true. This directly demonstrates reciprocal attribution is currently accepted; it does not establish a duplicate payout or a five-account farming outcome. The current pgTAP test covers self and conflicting attribution, not reciprocal/cyclic attribution. Gate 2 should set an abuse rule for cycles before any $5 delivery and test a reciprocal pair, a longer cycle, simultaneous fifth verification, and a withdrawn profile receipt. No referral payout adapter exists yet.

## Draft test checkout rate and auth review

Read-only review of Gate 2 [draft #153](https://github.com/rachelgonsalves821/EnvoiLabs/pull/153) at `3eb01fb` found the POST route default-off, requiring same-origin empty JSON, AAL2 researcher membership, a valid study ID, a trusted service client, an HTTPS app origin, and an `sk_test_` key before creating the provider adapter. The response is private/no-store and the service verifies the frozen quote, exact Stripe origin, amount and identity. Its local route tests cover disabled, cross-origin, non-MFA, missing researcher, response shape and blocked result. No live Stripe call was made in this review.

Gate 2 follow-up `99aac1094fa6b67e6f4919674f57699e58b3c631` adds an authenticated `POST /api/researcher/studies/[studyId]/checkout/reconcile` route. Source inspection confirms the same default-off flag, same-origin JSON parsing, AAL2 and study-organization checks before the service-only provider observer. Pending and uncertain refunds do not launch fieldwork: the observer now rejects non-settled refunds, and reconciliation records only a non-pending state. Its route tests use mocks and do not exercise a real provider. The new route calls `provider.getCheckout` on every authorized request, so the request-budget finding below applies to **both** checkout and reconciliation endpoints. Add a concurrent and repeated reconciliation fixture proving a denied call makes zero provider GETs, plus an uncertain-refund → settled-refund transition that retains the frozen quote and ledger identity. Keep the route disabled outside approved disposable test environments.

The route has no application-level request limit. `prepareStudyCheckout` uses a durable intent and idempotency key to prevent duplicate **creates**, but when `claimCheckoutIntent` returns `known`, every repeated POST calls `provider.get(checkoutId)`. A signed-in researcher can therefore force repeated Stripe lookups and database work for one study even though the logical checkout is unchanged. Before enabling the route, Gate 2 should choose a bounded per-researcher/study request budget or an authorized cached/reconciled response policy; the Gate 4 email/upload limiter has no checkout surface or migration policy. The two-process fixture should race many same-study POSTs, prove at most one create, then replay a known intent beyond the approved request budget and prove denied calls make zero provider requests, with generic no-store responses. Repeat for AAL1, wrong tenant, malformed ID and cross-origin requests. Coordinate any new limiter surface/migration with the sole Platform writer. This is an abuse/availability finding, not evidence of duplicate billing.
